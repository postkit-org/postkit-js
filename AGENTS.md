# PostKit repository guide

PostKit is a portable publishing toolkit. Public packages live under
`packages/`, the Next.js documentation site lives in `apps/site`, executable
examples live in `examples/`, and validation and release programs live in
`tools/`.

## Package boundaries

| Package                    | Responsibility                                                                   |
| -------------------------- | -------------------------------------------------------------------------------- |
| `@postkit/unfurl`          | Provider-neutral server/build-time metadata resolution                           |
| `@postkit/react`           | Portable declarations, React renderers, Markdown/MDX tooling, and Chakra recipes |
| `@postkit/shiki`           | Lazy Shiki adapter and curated syntax-highlighting defaults                      |
| `@postkit/next`            | Next.js link and MDX adapter                                                     |
| `@postkit/react-router`    | React Router link and MDX adapter                                                |
| `@postkit/tanstack-router` | TanStack Router link and MDX adapter                                             |
| `@postkit/astro`           | Astro integration, components, React bridges, and hydration policy               |

Dependency order is `unfurl` → `react` → framework adapters. Keep application
layout, route definitions, credentials, asset storage, and persistence outside
the portable component layer. `@postkit/shiki` is an optional companion adapter
passed into the React provider and does not change the core dependency chain.

## Sources of truth

- `packages/react/src/lib/declarations.ts` defines the portable component and
  prop contract.
- `packages/react/src/lib/component-catalog.ts` enriches declarations for
  discovery, examples, runtime requirements, and renderer support.
- `packages/react/component-manifest.json` is generated by
  `npm run catalog:generate`; never edit it directly.
- `libs/content/docs/` contains canonical task-oriented documentation.
- `apps/site/public/llms.txt`, `llms-full.txt`, and `postkit-docs.json` are
  generated by `npm run docs:agents:generate`; never edit them directly.
- Public package exports are the source for the generated TypeDoc API under
  `apps/site/public/api/`.

## Change invariants

- A portable component or prop change must update its declaration, renderer,
  tests, generated manifest, relevant package README, and Astro bridge when
  supported there.
- A public export must be reachable from the package's documented export map
  and must work from a packed clean consumer.
- Remote provider credentials and origin fetching stay in server, build, or
  trusted-editor code. React components consume normalized data.
- Provider `rawHtml` is untrusted and must not be injected by PostKit
  renderers.
- Plain Markdown directives accept allowlisted literal data, never authored
  JavaScript expressions.
- Interactive Astro bridges must declare and document their hydration policy.
- Examples must compile; do not add unvalidated README-only integration code
  when the same case can live under `examples/`.

## Validation

Use Nx targets for package work. Before handing off a cross-package change,
run the smallest affected targets and then the appropriate aggregate:

```sh
npm run check
npm run catalog:check
npm run examples:check
npm run docs:check
npm run site:check
npm run package:check
```

`npm run verify:release` is the full release gate. It also packs every public
package and verifies runtime and TypeScript entry points from a clean consumer.

# General Guidelines for working with Nx

- For navigating/exploring the workspace, invoke the `nx-workspace` skill first - it has patterns for querying projects, targets, and dependencies
- When running tasks (for example build, lint, test, e2e, etc.), always prefer running the task through `nx` (i.e. `nx run`, `nx run-many`, `nx affected`) instead of using the underlying tooling directly
- Prefix nx commands with the workspace's package manager (e.g., `pnpm nx build`, `npm exec nx test`) - avoids using globally installed CLI
- You have access to the Nx MCP server and its tools, use them to help the user
- For Nx plugin best practices, check `node_modules/@nx/<plugin>/PLUGIN.md`. Not all plugins have this file - proceed without it if unavailable.
- NEVER guess CLI flags - always check nx_docs or `--help` first when unsure

## Scaffolding & Generators

- For scaffolding tasks (creating apps, libs, project structure, setup), ALWAYS invoke the `nx-generate` skill FIRST before exploring or calling MCP tools

## When to use nx_docs

- USE for: advanced config options, unfamiliar flags, migration guides, plugin configuration, edge cases
- DON'T USE for: basic generator syntax (`nx g @nx/react:app`), standard commands, things you already know
- The `nx-generate` skill handles generator discovery internally - don't call nx_docs just to look up generator syntax
